# PC ↔ 폰 약속 (BLE 프로토콜)

PC(`src-tauri/`)와 폰 앱(`android/`)이 서로 맞춰야 하는 값은 전부 여기에 적습니다.
한쪽을 바꾸면 이 문서와 반대쪽 코드를 같이 바꿉니다. 코덱 번호 표는 [CODECS.md](CODECS.md).

| 값이 있는 곳 | PC | 폰 |
|---|---|---|
| UUID·광고 | `src-tauri/src/ble.rs`(Linux), `ble_windows.rs`(Windows) | `Protocol.kt`, `AudioService.kt`(스캔 필터) |
| QR 링크 | `src-tauri/src/link.rs` | `Protocol.kt` |
| 패킷 헤더·제어 메시지 | `src-tauri/src/codec/packet.rs` | `Protocol.kt` |
| 연결 확인 계산·순서 | `src-tauri/src/auth/` (계산), `listener.rs` (순서) | `Auth.kt` (주고받기는 `AudioService.kt`) |
| 코덱 번호 | `src-tauri/src/codec/mod.rs` | `Codecs.kt` |

## 1. 찾기: QR과 광고

| 항목 | 값 |
|---|---|
| 서비스 UUID | `5e7a0001-3c1b-4f6e-9d2a-7b1c0e5a9f10` |
| 오디오 특성 UUID (Notify + Write) | `5e7a0002-3c1b-4f6e-9d2a-7b1c0e5a9f10` |
| 광고 | 연결 가능, 서비스 UUID만. 주소는 PC의 진짜(고정) 블루투스 주소 |
| QR 링크 | `hearone://connect?id=<번호>&addr=<주소>&key=<열쇠>&name=<이름>` |

QR 링크 칸:
| 칸 | 형식 | 뜻 |
|---|---|---|
| `id` | 16진수 8자리 | PC 고유 번호. 폰 기록의 이름표(열쇠). 처음 실행할 때 무작위로 만들어 설정 폴더 `device_id`에 저장 |
| `addr` | 16진수 12자리 (콜론 없음, 예 `98fe3ee10527`) | PC 블루투스 주소. 폰은 이 주소로 연결. PC가 주소를 못 읽으면(블루투스 꺼짐) 빠짐 → 폰은 그 QR을 거절 |
| `key` | 16진수 64자리 (32바이트) | 확인용 열쇠 (5절). 처음 실행할 때 무작위로 만들어 설정 폴더 `secret`에 저장 |
| `name` | URL 퍼센트 인코딩(UTF-8) | PC 컴퓨터 이름(hostname). 폰은 처음 저장할 때만 씀 |

- 폰은 **QR로 받은 주소 + 서비스 UUID**가 맞는 광고를 찾아 연결합니다. 기록에 없는 PC는 찾지 않으므로 처음 연결은 QR로 합니다.
- 광고에 PC 번호를 싣지 않습니다. Windows 연결용 광고는 내용을 Windows가 채워 자리가 없고, 따로 낸 광고는 Windows가 가짜 주소를 붙여 연결할 수 없기 때문입니다 (CLAUDE.md 2026-10-07).
- 같은 PC의 Linux와 Windows는 주소가 같지만 `id`·`key`가 따로라 폰 기록에 두 개로 올라갑니다.

## 2. 연결

1. 폰이 QR 주소로 연결 → MTU 517 요청 → 서비스 찾기
2. 폰이 오디오 특성의 표준 CCCD(`00002902-0000-1000-8000-00805f9b34fb`)에 알림 켜기를 씀 = 구독
3. 연결 확인 (5절). 통과한 폰에만 PC가 Notify로 소리 패킷을 계속 보냄
4. 블루투스 페어링·암호화는 하지 않습니다 (특성에 보안 설정 없음). 소리 패킷은 잠그지 않은 채 나갑니다

## 3. 패킷

Notify 하나 = 패킷 하나. 최대 크기 = MTU − 3 (ATT 헤더), 20~512바이트로 제한.

| 바이트 | 내용 |
|---|---|
| `[0]` | 버전 = `1` |
| `[1]` | 코덱 번호 ([CODECS.md](CODECS.md)). **`0` = 제어 메시지** |
| `[2..4]` | 순번 u16 little-endian. 폰마다 따로 0부터 세고 65535 다음은 0. 손실 감지용 |
| `[4..]` | 코덱 데이터. 제어 메시지면 명령 1바이트 + 명령별 데이터 |

- 패킷 하나에 코덱 프레임 하나. 프레임이 MTU보다 크면 보내지 않고 버립니다.
- 버전이 다르거나 헤더보다 짧은 패킷은 폰이 버립니다.

## 4. 제어 메시지 (코덱 번호 0)

| 명령 `[4]` | 뒤 데이터 | 뜻 | 폰 동작 |
|---|---|---|---|
| `1` | 없음 | PC가 공유를 중지함 (공유 중지 버튼, 창 닫기) | 정지 버튼을 누른 것과 같이 멈춤. 다시 찾지 않음 |
| `2` | PC 무작위 값 16바이트 | 확인 문제 (5절) | 답을 씀 |
| `3` | PC 증명 32바이트 | 확인 통과 (5절) | PC 증명을 검사. 맞으면 소리 받기 시작, 틀리면 가짜 PC로 보고 끊음 |
| `4` | 없음 | 확인 실패: 열쇠가 다름 (5절) | 멈추고 "QR을 다시 찍어 주세요". 다시 찾지 않음 |

- 소리 패킷과 같은 통로로 보내므로 마지막 소리 뒤에 도착합니다.
- PC는 중지 패킷을 보낸 뒤 최대 0.5초 기다리고 0.2초 더 쉰 다음 연결을 정리합니다.
- 강제 종료·PC 꺼짐처럼 중지 패킷을 못 보내면 폰은 "끊김"으로 보고 다시 찾습니다.

## 5. 연결 확인

QR로 건넨 열쇠 K를 PC와 폰이 둘 다 가졌는지, 연결할 때마다 서로 확인합니다. 열쇠 자체는 공중으로 보내지 않습니다.

```
폰 ── 구독 ─────────────────────────────▶ PC
폰 ◀── 제어 2: PC 무작위 값 P (16B) ────── PC
폰 ── Write: 답 (50B) ───────────────────▶ PC   폰 증명을 검사
폰 ◀── 제어 3: PC 증명 (32B) ───────────── PC   (틀리면 제어 4, 소리 안 보냄)
     폰이 PC 증명을 검사 → 맞으면 소리 패킷이 이어서 옴
```

- 증명 = `HMAC-SHA256(K, 이름표 ‖ P ‖ F)`
  - 폰 증명의 이름표 = ASCII `hearone-phone`, PC 증명의 이름표 = ASCII `hearone-pc`
  - `F` = 폰이 이번 연결에 새로 만든 무작위 값 16바이트
- 폰의 답 (오디오 특성에 Write, 응답 있는 쓰기):

| 바이트 | 내용 |
|---|---|
| `[0]` | 버전 = `1` |
| `[1]` | 종류 = `1` (확인 답) |
| `[2..18]` | 폰 무작위 값 F |
| `[18..50]` | 폰 증명 |

- 확인 패킷 크기: 문제 21바이트(헤더 4 + 명령 1 + P 16), 통과 37바이트(헤더 4 + 명령 1 + 증명 32), 폰의 답 50바이트. 모두 기본 MTU(23, 한 번에 20바이트)보다 크므로 **폰은 구독 전에 MTU를 늘려야** 합니다 (2절 1번의 517 요청). 늘리지 않으면 PC가 문제를 보내지 못합니다.
- PC는 문제를 낸 뒤 5초 안에 맞는 답이 없으면 제어 4를 보내고 그 폰에는 소리를 보내지 않습니다.
- P와 F를 연결마다 새로 만들므로 예전 연결을 녹음해 다시 틀어도 통과하지 못합니다.
- 증명 비교는 걸리는 시간이 같은 방법으로 합니다 (PC는 `hmac`의 `verify_slice`).
- 폰은 구독한 뒤 10초 안에 확인이 끝나지 않으면 멈추고 "PC 앱을 업데이트해 주세요"를 보입니다 (옛 PC 앱은 문제를 보내지 않음).
- 구현 상태 (2026-10-07): 1·5절의 새 방식은 PC Linux(`ble.rs`)·Windows(`ble_windows.rs`), QR 링크(`link.rs`), 폰 앱 모두에 있음.
